# Estrategia de pruebas de RNC Web

Estado: estrategia local del MVP, con matrices acotadas al dominio sintético y evidencia de ejecución actualizada al 10-11-2026. Esta estrategia no constituye aprobación institucional ni certificación de seguridad, metodología epidemiológica o divulgación pública.

## Propósito y criterio de cobertura

Las pruebas deben descubrir defectos y demostrar que los recorridos implementados producen los resultados esperados. Cada caso debe enlazarse a un requisito, indicar datos y condiciones de entrada, describir el resultado esperado y registrar la ejecución. Los datos de prueba son sintéticos y no se reutilizan archivos locales de salud.

“100% probado” significa que todos los requisitos funcionales del MVP que estén dentro del alcance y sean verificables tienen casos asignados, que todos los casos bloqueantes y altos de la matriz pasan, y que no quedan fallos conocidos sin registrar. No significa que se hayan probado todas las combinaciones matemáticas posibles, que el software esté libre de defectos, o que pendientes institucionales se consideren aprobados. Toda brecha, regla pendiente o verificación que requiera personas/equipos externos se declara aparte.

## Niveles y responsabilidades

| Nivel | Qué aísla | Herramienta actual | Evidencia |
|---|---|---|---|
| Unidad | Cálculos, validadores y transformaciones sin flujo web | `SimpleTestCase` / pruebas Django | Salida del runner y valor de referencia sintético |
| Integración | Formularios, vistas, permisos, persistencia, archivos, publicación y exportación | `TestCase` con base de datos de prueba, almacenamiento temporal y correo local | `public_site/tests.py`, `analytics/tests.py`, salida de Django |
| Extremo a extremo | Navegador → formulario → backend → almacenamiento/cálculo → respuesta o descarga | `scripts/review_ui.py` con Playwright y Chromium headless | `docs/revision-completa-AAAA-MM-DD/` (ignorado por Git) |
| Manual complementaria | Lector de pantalla, teclado real, tareas con usuarios, operación en dispositivos, revisión de seguridad/rendimiento | Aún no automatizada | Requiere plan y participantes/entorno adecuados; no se cuenta como aprobada |

La suite del navegador usa una base SQLite temporal, cuentas sintéticas, correo a archivos locales, almacenamiento privado temporal y puerto loopback efímero; el proceso elimina estos recursos al terminar. La suite Django crea y destruye una base de prueba. Ninguna de las dos debe usar la BD local de desarrollo ni SMTP real.

## Ejecución reproducible

Desde la raíz de `rnc-web`, con `.venv` instalado:

```bash
rtk proxy .venv/bin/python manage.py test --verbosity 2
rtk proxy env RNC_REVIEW_BROWSER=/snap/chromium/current/usr/lib/chromium-browser/chrome .venv/bin/python scripts/review_ui.py
```

El primer comando ejecuta casos de analítica y aplicación en una base de datos desechable. El segundo levanta una aplicación local aislada, recorre los flujos en tres tamaños y guarda `resultados.json`, galería, exportaciones y capturas en `docs/revision-completa-2026-10-23/`. El reporte debe revisarse junto con el código; el conteo de checks es sensible a cambios y no equivale a cobertura de requisitos.

### Perfil rutinario con cobertura y casos extensos

Los casos de enumeración exhaustiva usan la etiqueta `long_running`: Coverage encarece mucho cientos de miles de llamadas. Se instrumenta la suite regular y después se ejecuta la matriz sin instrumentación:

```bash
rtk proxy .venv/bin/python -m pip install -r requirements-test.txt
rtk proxy .venv/bin/coverage run --branch manage.py test --exclude-tag=long_running --verbosity 2
rtk proxy .venv/bin/coverage report --show-missing --skip-covered
rtk proxy .venv/bin/python manage.py test --tag=long_running --verbosity 2
rtk proxy env RNC_REVIEW_BROWSER=/usr/bin/google-chrome-stable .venv/bin/python scripts/review_pwa.py
rtk proxy env RNC_REVIEW_BROWSER=/usr/bin/google-chrome-stable .venv/bin/python scripts/stress_pwa.py
rtk proxy env RNC_REVIEW_BROWSER=/usr/bin/google-chrome-stable .venv/bin/python scripts/review_ui.py
```

El E2E PWA crea servidor loopback temporal, perfil público, artefacto sintético y Chrome. Comprueba IndexedDB, paridad de consulta, 12 gráficos, CSV/PNG/PDF, caché, rutas administrativas y trabajo offline. La carga crea 28 800 filas sintéticas y un cubo temporal; no escribe en una base compartida. Los JSON se guardan bajo `docs/` (ignorado por Git); las cifras esenciales se transcriben al reporte fechado.

## Evidencia de la ejecución

### Matriz combinatoria ejecutada — 23-10-2026

Con el contrato sintético actual (2 años, 1 territorio, 2 sexos, 18 grupos etarios y 2 grupos de localización), se ejecutaron estas enumeraciones:

- **46 400 consultas de selector/filtro:** 320 cruces de dimensión × indicador × unidad × gráfico por 145 estados de filtro: sin selección y cada combinación de un valor de los cinco filtros (2 × 1 × 2 × 18 × 2 = 144).
- **262 158 estados multiselección:** todos los subconjuntos posibles de cada filtro, enumerados campo por campo, incluida cada una de las 262 144 selecciones de edad; se comprobaron invariantes de conteo.
- **750 exportaciones:** los cinco formatos (CSV, XLSX, PNG, SVG y PDF) para los 150 estados de selector compatibles con la consulta y la visualización. Los cuatro selectores restantes de los 154 aceptados por el formulario se rechazan por reglas de visualización/datos.
- `test_rendered_export_limit_allows_twenty_and_blocks_the_next` verifica que 20 exportaciones gráficas pasan y la 21.ª se rechaza con HTTP 429 y `Retry-After: 60`.

La combinación simultánea de todos los subconjuntos multiselección de los cinco filtros tiene **33 554 432** estados (4 × 2 × 4 × 262 144 × 4). No se ejecutó cada estado de ese producto ni su cruce con todos los selectores y formatos. Sí se recorrieron todos los estados de cada filtro por separado, todos los cruces con selección simple y los casos combinados multiselección ya definidos. Por tanto, esta ejecución no se etiqueta como cobertura literal del producto cartesiano completo. Los dominios de catálogos configurables externos tampoco son finitos hasta que se fije su contenido.

## Mantener la estrategia

1. Antes de cambiar una función, enlazarla a requisito, decisión o pregunta vigente en `rnc-research`.
2. Añadir primero un caso que falle ante el defecto (o un caso de aceptación observable en navegador), usando datos sintéticos.
3. Corregir la implementación y correr el caso focalizado; luego correr la suite completa del nivel afectado.
4. Para cambios de navegación, formulario, cálculo visible, exportación, permisos o publicación, correr el recorrido E2E completo.
5. Revisar salidas, errores JS, recursos estáticos, HTTP 5xx, tablas, exportaciones y capturas; registrar los fallos antes de corregirlos.
6. Actualizar esta matriz y la evidencia en `rnc-research/docs/evidence-map.md` solo después de observar el resultado. Mantener separados los hechos oficiales, las propuestas del prototipo y los temas que requieren validación del RNC.

La automatización detecta regresiones en los caminos codificados. La validación con el RNC, el estudio de riesgo de inferencia, pruebas con usuarios, lector de pantalla, seguridad, rendimiento, respaldos y operación productiva siguen siendo actividades independientes.

## Integración continua

`.github/workflows/tests.yml` ejecuta en paralelo la suite Django y el recorrido Chromium en cada push a `develop` y en cada PR hacia `main`. La PR debe revisarse con ambos resultados; el control de política de archivos sigue siendo independiente. Los reportes generados permanecen locales/efímeros y no suben datos ni capturas al repositorio. La rama protegida debe exigir ambos checks para convertirlos en un bloqueo efectivo de fusión.
